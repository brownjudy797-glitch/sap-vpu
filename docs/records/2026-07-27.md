# SAP-VPU Work Records - 2026-07-27 - DeiT Full-Dimension RTL and Labeled Validation

## Objective

Replace the four representative DeiT-Tiny output pairs with an optional sweep
of all 384 pairs, while preserving the four-pair fast regression.

## Implementation

- `DeitOutputPairs` selects 2 to 384 evenly distributed output pairs; 384 maps
  every channel pair from `(0,1)` through `(766,767)`.
- The transformer checker and SVH writer accept a dynamic pair count.
- Generated SVH arrays wrap at eight constants per line. This fixed Verilator's
  40,000-token line limit encountered by the initial full-layer fixture.
- DeiT metadata and weight testbench regions moved to non-overlapping high
  addresses sized for the full layer.
- `make sim-subsystem-deit-full-output` provides the dog-image full sweep. The
  existing `make sim-subsystem-deit-stream` remains the four-pair smoke.

## Boundary

This initial result is full output-channel coverage of the K=192 FC1 integer
matrix product for two image-derived tokens. The later all-token extension
closes the token dimension, but bias, GELU, later layers, labeled accuracy, and
end-to-end model execution remain outside the claim. The fixtures are
testbench data and are not synthesized into SAP-VPU hardware.

## Regression and Runtime Repair

The first 16-token run exposed two verification issues. The original fixed
watchdog was too short for 8 x 384 tiles, and `gate_fail` used `$finish`, which
allowed a failed simulation to return success. The watchdog now scales with
token and output-pair counts, and `gate_fail` uses `$fatal(1, ...)` so failures
propagate to Make.

Ubuntu 20.04's system Python 3.8 also produced nondeterministic interpreter
failures. A checksum-verified CPython 3.12.13 runtime is installed under ignored
`work/toolchain/python312`; Make uses it when present and otherwise falls back
to `python3`. Automatic `python.exe` fallback was removed because repeated WSL
interop processes stalled the environment. Make disables bytecode writes, and
the PowerShell model wrapper applies the same setting to Windows Python so
generated `__pycache__` files do not reappear under `scripts/`.

Post-fix regressions pass for:

- `make sim-subsystem-deit-token-sweep`
- `make sim-subsystem-deit-full-output`
- `make sim-subsystem-deit-stream`
- `make sim-subsystem-k512-stream`

## Davinci A7-200T Real-Board Hello

Legacy `nutvpu` constraints identified the real board as Davinci Pro A7-200T,
device `xc7a200tfbg484-2`, with 50 MHz clock R4, active-low reset U7, UART
E14/D17, and LEDs V9/Y8/Y7/W7. A new `sap_vpu_davinci_top`, XDC, Verilator
serial testbench, Windows Vivado build wrapper, and JTAG/UART smoke target were
added.

The first full-SoC synthesis failed placement at 142722 LUTs because the 4 KiB
RAM was implemented as 32768 FFs plus a large asynchronous read mux. CPU data
and VPU DMA requests are mutually exclusive, so the SoC now shares one
synchronous RAM access path. Vivado infers one 1Kx32 RAMB36, and all hello,
VPU, tiled-GEMM DMA, and board-top simulations still pass.

The first programmed image fetched zero instructions. Board diagnostic packets
showed PC cycling through 0x0/0x4/0x8 with instruction data zero. The
post-synthesis netlist retained ROM initialization only on one automatically
duplicated read port. Explicit instruction/data ROM copies fixed instruction
fetch; removing the VPU error path's invalid ROM read made the CPU data ROM a
single initialized port and fixed string loads.

Final evidence:

## Davinci VPU and Tiled-GEMM DMA Workloads

The board build was parameterized by ROM image, and the JTAG/UART runner gained
a post-program buffer discard mode for status-only workloads. This prevents a
previously programmed image from satisfying the next image's success check.

| Image | WNS ns | LUT | FF | BRAM | DSP | Real-board status |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| VPU instruction smoke | +0.507 | 7660 | 4558 | 1 | 3 | `P000000E4I02B7BFF5SF` |
| Tiled-GEMM DMA smoke | +0.965 | 7799 | 4558 | 1 | 3 | `P00000280IBFF51050SF` |

Both images passed `xc7a200t_0` JTAG programming and CH340 COM5 capture at
115200 baud. `SF` means the design observed instruction and data requests,
reached exit MMIO, and received success code 1. The VPU smoke covers base dot
product, adaptive precision, sparse bitmap, lane control, and counters. The
tiled-GEMM DMA smoke covers RAM reads/writes, autonomous operand movement,
K5/K8/tail/sparse tiles, output stores, and skip counters. This is now a real
board execution result, not only RTL simulation or OOC timing.

## Current-RTL Davinci Clock Sweep

The first 80 MHz full-SoC implementation exposed a 16.501 ns, 21-level
combinational path from CV32E40X execution control through CV-X-IF into the VPU
stream FSM and failed at -4.307 ns WNS. A one-entry registered command buffer
was added to `cvxif_sap_vpu_adapter`; it adds one custom-instruction launch
cycle while preserving the existing one-in-flight contract. Adapter, VPU,
tiled-GEMM DMA SoC, and Davinci hello regressions pass after the change.

With the registered boundary, 80 MHz improves to -1.499 ns WNS after
post-route `AggressiveExplore`. The remaining 13.931 ns path runs through the
CV32E40X load/store and scalar multiply forwarding network into the adapter
`rs2` register. The path is real: no false-path or multicycle exception was
added, and 100 MHz was not run as a candidate passing main configuration.
